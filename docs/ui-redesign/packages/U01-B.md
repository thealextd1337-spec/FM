## Minimaler Vorschlag für `projection.players`

Die View liest keine Karriereglobals und bekommt keine Rohspieler. Die folgende Kaderprojektion genügt für eine erste idempotente DOM-Ergänzung. Alle Texte sind unescaped Eingabetexte, die Komponenten escapen; kein beliebiges HTML als Spielerfeld.

```js
{
  season: 1,
  ownClubId: 'opaque-club-id',
  roster: [{
    id: 'opaque-player-id', name: 'Beispielname', number: 7,
    nationCode: 'DE', nationLabel: 'Deutschland',
    positionCode: 'mid', positionLabel: 'Mittelfeld', age: 24,
    skills: [{ key: 'passing', label: 'Passspiel',
               band: 'yellow', colorLabel: 'Gelb' }],
    form: { band: 'orange', label: 'gut' },
    freshness: { percent: 82, band: 'orange', label: 'Frische' },
    stats: {
      appearances: 6, substitutions: null,
      substitutionCoverage: 'missing',
      goals: 1, assists: 2, averageRating: 6.4, ratedGames: 5
    }
  }]
}
```

Beispielzahlen illustrieren nur das Schema, sie sind keine Fixture-/Regelautorität. `substitutions` und `averageRating` sind nullable. Fehlende Frische/Form dürfen als `null` oder mit unbekanntem Band projiziert werden; kein erfundenes gesundes/volles Ersatzsignal. `positionCode` ist `gk|def|mid|att`, Skills enthalten nur vorhandene bekannte Fähigkeiten. Fähigkeiten können alternativ mit `band:null`, `colorLabel:'Nicht bekannt'` vollständig benannt werden, wenn der Komponentenvertrag den unbekannten Zustand so festlegt. Keine Schlüssel `value`, `rating` für Fähigkeiten, `potential`, `talent`, `developmentMinutes`, Roh-`history` oder beliebig ausgebreitete Spielerobjekte.

## Profilprojektion als zweite kleine Ergänzung

Bestehende Profilinhalte und ihre Controller bleiben zunächst vollständig im Originaldialog. Für gezielte Modernisierung braucht I00 einen eindeutigen, transienten Profilkontext; PID-Abgleich über Namen ist ausgeschlossen. Vorschlag: `projection.players.profile` ist `null` oder folgendes bereits bereinigtes Objekt, wenn das Profil offen ist. I00 darf statt Vorhalten aller Profile bei jedem Profilöffnen separat projizieren.

```js
{
  playerId: 'opaque-player-id', kind: 'professional', // youth|start|retired|simulation
  identity: { name, number, nationCode, nationLabel, positionLabel, age },
  skills: [], form: null, freshness: null,
  owner: { id, name, status: 'club' }, // free|retired|simulation|youth
  marketValue: null,
  contract: null, // { annual, fromSeason, endSeason, remainingSeasons, promise }
  seasonStats: {
    season, appearances, minutes, goals, assists,
    shots: { value: null, recordedMatches: 0, totalMatches: 0 },
    tackling: { won: null, attempts: null, percent: null,
                recordedMatches: 0, totalMatches: 0 },
    averageRating: null, ratedGames: 0
  },
  career: [{ season, clubId, clubName, games, minutes, goals, assists }],
  honours: [{ kind, label, season, clubName, count: 1 }],
  gaps: [] // übersetzbare Kennzeichnungen, keine Rohrecords
}
```

Profilquelle ist `v68OpenPlayerProfile` (`world-views-v68.js:248`) plus `v127SeasonStatsHTML`, `v68PlayerRows` und `v74PlayerHonoursHTML`. `v66Player` löst roster/freePlayers/retiredPlayers auf, aber **nicht youthPool**. Nachwuchspfad in `world-youth-ui-v67.js:176` liest den eigenen Pool direkt. Startprofile nutzen generierten, noch nicht gespeicherten Startkader. Eine reine read-only Resolverfunktion im Adapter darf diese eindeutigen Quellen zusammentragen, nicht neue persistente Spieler erzeugen.

Historische Saisonzeilen aus `player.seasons` sind nach Saison/Verein verdichtet. Aktuelle `history` separat aggregieren, ohne überlappende Saison/Vereinszeilen doppelt zu zählen. Alte Summaries haben weder Ratingabdeckung noch Einwechselzahlen oder Wettbewerbsbezug. Keine neuen „vollständigen“ Karrierequoten aus diesen Lücken berechnen. `0`, `–` bei keinem Versuch und „Nicht erfasst“ unterscheiden. Persönliche Awards/MotM/Teamtitel bleiben getrennt; vorhandene Mannschaftstitel nicht rückwirkend verleihen.

## Lieferung und Nachweise

Der freigegebene Adapter liefert `roster` und `all`; Profilzuordnung läuft über `dialog.dataset.flPlayerId`. Die oben beschriebene größere separate Profilprojektion wurde **nicht** benötigt oder implementiert: native Saisonstatistik, Karriere/Awards, Vertragsfakten und Transferaktionen bleiben im Dialog erhalten. Ergänzt sind gemeinsame qualitative Fähigkeiten sowie Form/Frische. Nur der alte Fähigkeitsblock samt Legende wird zugunsten der vollständigen qualitativen Komponenten ausgeblendet.

Kader behält genau eine ursprüngliche `tr` je Spieler, sämtliche nativen Sortier-/Profilattribute und deren DOM-Nodes. Fähigkeiten/Form/Frische liegen in derselben Namenszelle; Suche und Position blenden nur Zeilen aus. Filter bleiben bei Adapterrefresh erhalten. Einwechselzahlen werden nur bei explizit vollständiger Projektion ausgegeben, ansonsten mit Strich und Erklärung. Weder View noch Fixtures enthalten Rohfähigkeiten oder greifen auf Karriereglobals zu.

Markup wird per WeakMap-Signatur nur bei tatsächlicher Inhaltsänderung ersetzt. Wiederholtes Enhance erhält die Fähigkeitsnodes und einen fokussierten Statistik-Tooltip. Profilergänzung bearbeitet nur offene, eindeutig annotierte Dialoge. Zusätzliche Labels liegen in `work/ui-redesign/packages/U01-B/labels.json` für I00.
